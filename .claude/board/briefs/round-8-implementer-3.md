Plan:
1. `work_map_update.py`, pure (no I/O, no LLM, inputs never mutated: `copy.deepcopy`), with a module docstring in the style of `work_map_diff.py` explaining the rules below. Public: `update(parent: dict, new: dict) -> {"map": dict, "changes": {...}, "gaps": [str]}`.
2. The updated map: start from a deep copy of `new`'s top-level fields (task, transcript, duration... B-23 decides what to keep), with `task` falling back to the parent's when the new one is blank, and `steps`, `guardrails`, `open_questions` rebuilt:
   - Steps in the new session's order: a `same` pair → the parent's step unchanged (its `id`, `at`, quotes, everything) with `"source": "parent"`; a `differs` pair → the new step with the parent's `id`, `"source": "new"` and `"changed": [field names]`; an `only_b` step → the new step with a fresh id (`s<n>` with n above the highest numeric suffix used by the parent's ids, so ids never collide with the parent's), `"source": "new"`, `"added": True`. Then every `only_a` (parent-only) step, after the others, as the parent's step with `"source": "parent"`, `"removed": True`.
   - Guardrails the same way with `g<n>`. Their `step` field must point at an id in the updated map: for an item taken from `new`, map the new step id to its output id (parent id for paired steps, fresh id for added ones); for an item kept from the parent, keep its parent step id if that step is still in the output (removed steps stay in the output, flagged, so it is). Anything that doesn't resolve becomes `""`.
   - `source` tells B-23/B-09 which recording an item's `at` refers to; document that.
   - `open_questions` = the gaps (step 4) first, then the new map's own open questions, dropping blanks and case/space repeats.
3. `changes` = `{"new": [...], "changed": [...], "removed": [...], "unchanged": [...]}`, each a list of `{"section": "steps"|"guardrails", "id": <id in the updated map>, "title": <step title or rule>}`, with `"fields": [names]` added on `changed` entries; in map order, steps before guardrails.
4. `gaps`: debrief questions only about new, changed and removed items, never about unchanged ones, at most `MAX_GAPS = 8` (named constant), steps before guardrails, in map order. Fixed templates as named constants, worded like `gap_question` and labelled with `work_map_links._label` (rule text for guardrails; decision, else title, for steps):
   - added step: "This time you {label}. What made you add that?"; added rule: "This time you said {label}. When does that apply?"
   - removed step: "Last time you {label}. Do you still do that?"; removed rule: "Last time you said {label}. Does that still apply?"
   - changed: one question per item, for its most telling field in this order: guardrail `rule`, `numbers`, `applies_when`, `kind`, `ask_whom`, `step`; step `decision`, `judgment`, `reason`. Ignore a step's `guardrails` field when choosing (the rule's own question covers it), and skip the item if that was its only changed field. Template, e.g. for numbers "Last time {label} was {old}; now it's {new}. What changed?" and for text fields "Last time you {old_label}; now you {new_label}. What changed?"; pick sensible wording per field kind but keep them short and fixed (no LLM).
   Keep the helper that words a question separate (`_question(...)`) so B-23 can reuse it.
5. Edge cases to handle and test: parent with no steps (everything is new), new map with no steps (everything removed, nothing added), identical maps (no gaps, `changes` all `unchanged`, the updated map's steps equal the parent's plus `"source": "parent"`), items without ids, a new-session guardrail attached to a new step, a parent guardrail attached to a removed step, more than 8 candidate gaps (capped, steps first).
