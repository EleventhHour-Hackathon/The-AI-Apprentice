Goal: when an expert presses "Record again" on a confirmed Work Map and records the task a second time, the debrief asks the questions kept for them first, then only about what changed since last time. Once they confirm, the update to the original map is computed and stored, and one explicit call applies it to the original map, keeping its ids. The UI (change badges, an "Apply to the original map" button) is B-09, next round. It builds against the contract below.
Brief says: Moonshot, "A living company memory. Every expert and every workflow in one map that stays current. When the work changes, the apprentice asks only about what is new." (docs/CHALLENGE.md, Stretch goals list).

Plan:
1. `follow_ups.py`: add `LIVING_UPDATE = "living_update"` and `LIVING_APPLIED = "living_applied"` to the constants and to `NOT_FOR_MERGE`, and to the reserved tuple in `path_router.add_capture` (so a client tool can't forge them; 422 as today). Update the module docstring in one sentence.
2. `living_map.py` (pure, no I/O, inputs never mutated):
   - `fingerprint(work_map) -> str`: sha256 hex of `json.dumps({"steps": ..., "guardrails": ...}, sort_keys=True, ensure_ascii=False, default=str)` of the map's steps and guardrails (missing → []).
   - `capture(parent_id, parent, result, now) -> dict`: `{"kind": LIVING_UPDATE, "parent_work_map_id": parent_id, "parent_fingerprint": fingerprint(parent), "changes": result["changes"], "map": {"task": ..., "steps": ..., "guardrails": ...}, "at": iso seconds}` (steps/guardrails/task from `result["map"]`, deep-copied; not the whole map: no transcript).
   - `latest(captures, parent_id) -> dict | None`: the last LIVING_UPDATE capture for that parent (a session re-confirmed twice keeps the newest).
   - `applied(parent, stored, session_id) -> dict`: the parent row to save: a deep copy of `parent` with `steps`/`guardrails` from `stored["map"]`, every item whose `source == "new"` tagged `"from_session": session_id` (its `at` is a moment of that session's recording, not the parent's); the parent's own transcript, duration, corrections, confirmation and open_questions kept; `task` from the stored map only when the parent's is blank.
   Module docstring: what the living update is, that applying is a person's explicit step, and why `from_session` exists.
3. `merge_session` (path_router.py): after `merge(...)` and the `work_map.update(...)` of task/transcript/etc., when there is a parent and `parent.get("status") == "confirmed"`, run `result = work_map_update.update(parent, work_map)` inside try/except (on any exception: `logger.warning`, behave exactly as B-38 does today). Then:
   - draft: `work_map["open_questions"] = follow_ups.lead_with(pending, result["map"]["open_questions"])` (kept follow-ups first, then the changes' gaps, then the draft's own gaps). This replaces the B-38 line for this case; a draft parent (status "draft") keeps B-38's behaviour unchanged.
   - final: save the session's own map exactly as today (it stays a separate map under its own id), keep the B-38 "delivered" block, then `work_map_store.add_capture(session_id, living_map.capture(parent_id, parent, result, now))`. If that capture fails, `logger.error` and omit `living_update` from the response (the session map is saved; there is nothing to apply).
   - Response: add `"living_update": {"parent_work_map_id": parent_id, "changes": result["changes"]}` on draft and final whenever the update ran (and, on final, was stored). Without a parent, or with a non-confirmed parent, the response has no `living_update` key and is otherwise byte-identical to today.
   - `_with_moments`: skip items with a `from_session` field (no thumb, event or clip from the parent's screen events, which would be the wrong frame). One `continue`, with a comment.
   Redaction: every text in `update`'s output comes from the already-redacted merge or the stored parent; nothing new leaves the machine. Do not add any LLM call.
4. `living_map_router.py`: `router = APIRouter(prefix="/api/v1", tags=["Living map"])`; plain `def` endpoint `POST /work_maps/{work_map_id}/apply_update` with query `from` (`session: str = Query(..., alias="from")`). Use `_uuid` and `_store_unavailable` from `src.router.path_router` (as `follow_ups_router.py` does). Order of checks: bad UUIDs → 404 (`_uuid`); parent row missing → 404 "Work Map not found"; session row missing → 404 "Session not found"; `living_map.latest(session captures, parent id)` is None → 422 "This session has no update for that Work Map"; `fingerprint(parent) != stored["parent_fingerprint"]` → 409 "The Work Map changed since this update was made. Record it again to update it."; store errors → 503 via `_store_unavailable`. Then `save_map(parent_id, living_map.applied(parent, stored, session_id), "confirmed")` and `add_capture(parent_id, {"kind": LIVING_APPLIED, "from_session": session_id, "changes": stored["changes"], "at": now})`. Response 200: `{"work_map_id": parent_id, "applied_from": session_id, "changes": stored["changes"]}`. A second apply of the same update gets 409 (the parent's fingerprint changed), which is the intended guard against double-applying.

Contract (for B-09 next round; write it exactly):

- Capture kinds `living_update` (on the session) and `living_applied` (on the parent), both in `follow_ups.NOT_FOR_MERGE` and refused on `/capture`.
- After apply, parent items keep the M-01 flags (`source`, `changed`, `added`, `removed`), and `source: "new"` items carry `from_session`.
